# Add Error Handling and Update GitHub Actions to Latest Versions

## Problem Description

The current GitHub Actions workflows in this repository have several issues that need to be addressed:

1. **Outdated Action Versions**: The workflows reference older or unpinned action versions:
   - `actions/checkout@v3` (latest stable is v4+)
   - `lowlighter/metrics@latest` (unpinned, potentially unstable)
   - Various third-party actions with non-standard version tags

2. **No Error Handling**: Workflows lack proper error handling mechanisms:
   - No `continue-on-error` flags where appropriate
   - No failure notifications or status reporting
   - No retry logic for transient failures
   - Missing timeout configurations

3. **Security Concerns**: Using `@latest` or branch references (`@master`) instead of pinned SHA or semantic versions introduces supply chain risks.

4. **Inconsistent Workflow Triggers**: The `blank.yml` workflow uses non-standard trigger names (`workflow_dispatch`, `push`) instead of canonical GitHub Actions syntax.

## Proposed Solution

1. **Update all GitHub Actions to latest stable versions** with pinned semantic version tags or commit SHAs
2. **Implement comprehensive error handling** including:
   - Timeout limits for long-running jobs
   - Failure step notifications
   - Conditional execution based on previous step outcomes
   - Proper cleanup on failure
3. **Standardize workflow trigger syntax** to use official GitHub Actions event names
4. **Add workflow-level and job-level error reporting** for better debugging

## Implementation Steps

1. Update `actions/checkout` from `@v3` to `@v4` (latest stable)
2. Pin `lowlighter/metrics` to a specific version tag (e.g., `@v3.28` or latest stable SHA)
3. Replace non-standard trigger syntax:
   - `workflow_dispatch:` → `workflow_dispatch:` (under `on:`)
   - `push:` → `push:` (under `on:`)
4. Add `timeout-minutes` to jobs to prevent indefinite hangs
5. Add error handling steps:
   - Failure detection step using `if: failure()`
   - Status reporting via GitHub API or external notification service
6. Add `continue-on-error: true` where appropriate for non-critical steps
7. Implement retry logic for network-dependent operations using `retry` action or custom logic
8. Add workflow run conclusions to job outputs for downstream dependency tracking
9. Test all workflows in a dry-run scenario before merging

## Acceptance Criteria

- [ ] All action references use pinned semantic versions (e.g., `@v4`, `@v3.28.0`) or commit SHAs
- [ ] `actions/checkout` updated to `@v4` or latest stable
- [ ] `lowlighter/metrics` pinned to specific stable version (not `@latest`)
- [ ] All jobs have `timeout-minutes` configured
- [ ] Workflow triggers use canonical GitHub Actions syntax (`on:`, `workflow_dispatch:`, `push:`, `schedule:`)
- [ ] Failure handling step added with `if: failure()` condition
- [ ] Error reporting mechanism implemented (GitHub status, comment, or external notification)
- [ ] Non-critical steps have `continue-on-error: true` where appropriate
- [ ] All workflows pass validation via `act` or GitHub Actions linting tools
- [ ] Workflows execute successfully on manual trigger (`workflow_dispatch`)
- [ ] Scheduled runs complete without errors for at least one full cycle
- [ ] Documentation updated to reflect new error handling behavior
